# Integrate Skills Specification

**Scope**: Large

**Grilling Record**: [`.specs/decisions/0001-integrate-grill-into-spec-driven.md`](../../decisions/0001-integrate-grill-into-spec-driven.md)

## Problem Statement

Planning a feature takes two skills that overlap and disagree. `/grill-with-docs` gets the most complete requirements but writes no spec. spec-driven owns the spec, gates and reviewers, but its own questioning is shallower. They also keep two decision logs (ADRs and `STATE.md` `AD-NNN`), which models fill with one-paragraph entries. Several vendored skills still route work around spec-driven, and `grilling` is missing from opencode at work. Merge the specification phase into one grill inside spec-driven. Record every grilling session completely. Give spec-driven day-sized Tickets for the product team, and make spec-driven the only implementation path.

## Existing Capabilities

It found no planning material from other flows: no `.kiro/`, `openspec/`, `rfcs/`, `AGENTS.md` or `CLAUDE.md`. Only this repo's own `docs/adr/` and `CONTEXT.md` turned up.

The graph has no code-level equivalents. `graphify update .`, then `graph_queries.py symbols --match`:

## User Stories

### P1: One grill inside Specify ⭐ MVP

**User Story**: As a developer planning a feature, I want spec-driven's Specify to grill me one question at a time, so that I get grill-with-docs-quality requirements straight into a reviewed spec.

**Why P1**: This is the merge the user asked for.

**Acceptance Criteria**:

1. **GRILL-01**: WHILE Specify is gathering requirements, the agent SHALL ask exactly one question per turn, each with concrete options and one recommended answer.

   ```gherkin
   Scenario: GRILL-01.S1 one question per turn
     Given a repository with spec-driven installed
     And the user asks to specify "add CSV export to the orders page"
     When the agent grills the user until shared understanding
     Then every agent turn contains exactly one question
     And every question lists its options and marks one as recommended
   ```

2. **GRILL-02**: WHEN the user answers a question with "you decide" THEN the agent SHALL record its recommended option as that question's Decision with `Decided by: agent`.

   ```gherkin
   Scenario: GRILL-02.S1 you decide
     Given Specify asks "Which delimiter does the export use?" with "comma" recommended
     When the user replies "you decide"
     Then the Grilling Record holds a Decision choosing "comma"
     And that Decision reads "Decided by: agent"
   ```

3. **GRILL-03**: WHEN the user answers "decide the rest" THEN the agent SHALL list its default for every remaining branch in one turn and wait for overrides.

   ```gherkin
   Scenario: GRILL-03.S1 decide the rest
     Given Specify has three unasked branches left: file name, encoding, column order
     When the user replies "decide the rest"
     Then the next agent turn lists one default for each of file name, encoding and column order
     And the agent writes nothing to spec.md until the user replies
   ```

4. **GRILL-04**: WHEN Specify starts THEN the agent SHALL run the graphify capability search and report any Redundant Feature before its first question.

   ```gherkin
   Scenario: GRILL-04.S1 redundant feature first
     Given a repository whose src/export/csv.py already exports orders to CSV
     When the user starts Specify for "add CSV export to the orders page"
     Then the agent's first message names src/export/csv.py as an existing capability
     And it asks what the user needs beyond it before any other question
   ```

5. **GRILL-05**: IF a spec has no `## Decisions & Assumptions` section THEN `validate_spec.py` SHALL exit 1 and name that section, at every scope.

   ```gherkin
   Scenario: GRILL-05.S1 small spec without the section
     Given a Small-scope spec.md with every Small section except "Decisions & Assumptions"
     When validate_spec.py runs on it
     Then it exits 1
     And its output names "Decisions & Assumptions"
   ```

   ```gherkin
   Scenario: GRILL-05.S2 large spec with the old heading
     Given a Large-scope spec.md whose assumptions section is titled "Assumptions & Open Questions"
     When validate_spec.py runs on it
     Then it exits 1
     And its output names "Decisions & Assumptions"
   ```

6. **GRILL-06**: WHEN a spec's `## Decisions & Assumptions` section contains only `none` THEN `validate_spec.py` SHALL accept that section.

   ```gherkin
   Scenario: GRILL-06.S1 none is allowed
     Given a valid Small-scope spec.md whose "Decisions & Assumptions" section reads "none"
     When validate_spec.py runs on it
     Then it exits 0
   ```

7. **GRILL-07**: The spec-driven flow SHALL NOT write a per-feature `context.md`.

   ```gherkin
   Scenario: GRILL-07.S1 gray areas land in the spec
     Given a Specify session for "add CSV export" in which the user chose "download, not email"
     When the agent writes the spec
     Then .specs/features/csv-export/ contains spec.md and no context.md
     And spec.md's Decisions & Assumptions table has a row choosing "download, not email"
   ```

8. **GRILL-08**: IF the harness cannot load the `grilling` skill by name THEN Specify SHALL read `grilling/SKILL.md` from the skills directory that contains spec-driven.

   ```gherkin
   Scenario: GRILL-08.S1 sibling fallback
     Given grilling and spec-driven are installed side by side
     And the harness offers no tool to load a skill by name
     When the user starts Specify
     Then the agent reads grilling/SKILL.md next to the spec-driven directory before its first question
   ```

**Independent Test**: Run Specify on a fixture request and inspect the turns, the Grilling Record and the spec.

### P1: Complete Grilling Records ⭐ MVP

**User Story**: As a developer working mostly alone with an agent, I want every grilling session recorded in full under `.specs/decisions/`, so that the reasons and rejected options survive compaction, later sessions and teammates.

**Why P1**: It replaces both decision logs; without it the grill's output is lost.

**Acceptance Criteria**:

1. **REC-01**: WHEN a grill receives its first answer THEN the agent SHALL create `.specs/decisions/<NNNN>-<slug>.md`, numbered one above the highest existing record, with that question and answer in its Session path.

   ```gherkin
   Scenario: REC-01.S1 first answer creates the record
     Given .specs/decisions/ contains 0003-billing-retries.md
     When the user answers the first Specify question for feature csv-export
     Then .specs/decisions/0004-csv-export.md exists
     And its Session path holds that question, its options, the recommendation and the answer
   ```

2. **REC-02**: WHEN the user answers a later question THEN the agent SHALL append it to the Session path before asking the next question.

   ```gherkin
   Scenario: REC-02.S1 incremental append
     Given 0004-csv-export.md holds two answered questions
     When the user answers the third question
     Then 0004-csv-export.md holds three answered questions before the fourth question is shown
   ```

3. **REC-03**: WHEN the user confirms shared understanding THEN the agent SHALL complete the record's Decisions and Consequences and add its `summary.md` row before writing `spec.md`.

   ```gherkin
   Scenario: REC-03.S1 summary row before spec
     Given a csv-export grill with six answered questions
     When the user confirms shared understanding
     Then summary.md has a row for 0004-csv-export.md with a one-to-two-sentence Summary, Status "active", Binds, Areas and Specs "csv-export"
     And spec.md's Decisions & Assumptions rows link to D-0004 anchors in that record
   ```

4. **REC-04**: The Grilling Record SHALL contain Context, Session path, Decisions, Consequences and Related sections, and every Decision SHALL state choice, reason, trade-off, Binds, Decided by and Status.

   ```gherkin
   Scenario: REC-04.S1 complete record
     Given a finished csv-export grill in which the user rejected "email the file"
     When the record is complete
     Then it has the sections Context, Session path, Decisions, Consequences and Related
     And the Session path lists "email the file" as a rejected option
     And every Decision lists choice, reason, trade-off, Binds, Decided by and Status
   ```

5. **REC-05**: WHEN an accepted Finding changes a Decision THEN the agent SHALL append an `## Amendments` entry with the next Decision ID, mark the old Decision superseded, and update the `summary.md` row.

   ```gherkin
   Scenario: REC-05.S1 amendment from a Spec Review
     Given 0004-csv-export.md holds D-0004.3 "new Price type" and its last Decision is D-0004.6
     And Finding SR1-F2 recommends reusing Money
     When the user records "accept F2"
     Then 0004-csv-export.md has an Amendments entry adding D-0004.7 that cites SR1-F2
     And D-0004.3 reads "superseded by D-0004.7"
     And the summary.md row reads "partly superseded: D-0004.3 by D-0004.7"
   ```

6. **REC-06**: WHEN Design makes a choice THEN the agent SHALL record it under `## Design` in the feature's Grilling Record with the next Decision ID, and `design.md` SHALL link to it.

   ```gherkin
   Scenario: REC-06.S1 design decision
     Given 0004-csv-export.md ends at D-0004.6
     When Design chooses to stream rows instead of building the file in memory
     Then 0004-csv-export.md has a Design section with D-0004.7 choosing streaming
     And design.md's Tech Decisions links to D-0004.7
   ```

7. **REC-07**: WHERE `docs/adr/` or a `.specs/STATE.md ## Decisions` section exists, `summary.md` SHALL carry one legacy line per path.

   ```gherkin
   Scenario: REC-07.S1 legacy lines
     Given a repository with docs/adr/0001-postgres.md and a STATE.md Decisions section with AD-001
     And no .specs/decisions/ directory
     When the first Grilling Record is written
     Then summary.md has a legacy line naming docs/adr/
     And a legacy line naming .specs/STATE.md
   ```

8. **REC-08**: The spec-driven flow SHALL NOT write ADR files or `AD-NNN` entries.

   ```gherkin
   Scenario: REC-08.S1 no ADRs
     Given a repository with docs/adr/ and a STATE.md Decisions section
     When Design records a project-binding Decision
     Then no new file appears under docs/adr/
     And STATE.md gains no AD entry
     And the Decision is in the feature's Grilling Record
   ```

9. **REC-09**: WHEN a `/grill-with-docs` session that is not about a feature ends THEN it SHALL leave a Grilling Record whose `summary.md` row has Specs `none`.

   ```gherkin
   Scenario: REC-09.S1 non-feature grill
     Given the user runs /grill-with-docs on "should billing move to events?"
     When the user confirms shared understanding
     Then a new Grilling Record exists under .specs/decisions/
     And its summary.md row reads Specs "none"
   ```

**Independent Test**: Run a short grill on a fixture repository and inspect `.specs/decisions/` after each answer.

### P1: One read rule and repo discovery ⭐ MVP

**User Story**: As a developer on a large team repository, I want every skill to find the Decisions that bind the code it touches, and to notice teammates' planning material from other flows, so that nothing binding is silently ignored.

**Why P1**: Without it, the records are written but never read.

**Acceptance Criteria**:

1. **READ-01**: WHEN a consumer starts work on paths in a repository with `summary.md` THEN it SHALL open exactly the records whose rows are `active` or `partly superseded` and either bind the project with Areas overlapping those paths or `*`, or name its feature in Specs.

   ```gherkin
   Scenario: READ-01.S1 filtered read
     Given summary.md rows: 0001 project src/billing/ active; 0002 project * active; 0003 project src/billing/ superseded by 0005; 0004 feature src/ui/ active for feature dark-mode
     When tdd starts a Task touching src/billing/invoice.py for feature invoice-pdf
     Then the agent opens 0001 and 0002
     And it does not open 0003 or 0004
   ```

2. **READ-02**: WHEN a consumer starts THEN it SHALL run the two `fd` discovery listings and name any planning or decision material from other flows that bears on its work.

   ```gherkin
   Scenario: READ-02.S1 outside flows found
     Given a repository with a gitignored .kiro/specs/payments/ directory and a tracked docs/rfcs/0007-ledger.md
     When Specify starts for a feature that touches payments
     Then the agent names .kiro/specs/payments/ and docs/rfcs/ before its first question
     And the Grilling Record's Context cites the sources it used
   ```

3. **READ-03**: IF `fd` is not installed THEN the consumer SHALL stop and ask the user to install `fd` before continuing.

   ```gherkin
   Scenario: READ-03.S1 fd missing at runtime
     Given a machine where fd is not on PATH
     When the user starts Specify
     Then the agent's first message asks the user to install fd
     And it asks no planning question until fd is available
   ```

4. **READ-04**: IF `fd` is not on PATH THEN `install.sh` SHALL print a warning naming `fd` and still finish the install.

   ```gherkin
   Scenario: READ-04.S1 fd missing at install
     Given a PATH without fd and an empty temporary Claude config directory
     When install.sh runs
     Then it exits 0
     And its output warns that fd is missing
   ```

**Independent Test**: Run a consumer on a fixture repository with a known `summary.md` and outside-flow folders.

### P1: Reviews see the records ⭐ MVP

**User Story**: As the human running `/spec-review` and `/code-review`, I want the reviewers to judge the plan and the Change against the Grilling Records, so that dropped answers, agent-made choices and thin records get flagged.

**Why P1**: The reviewer is the only completeness guard (D-0001.6).

**Acceptance Criteria**:

1. **REV-01**: WHEN `prep_review.py spec` makes its snapshot commit THEN the commit SHALL include uncommitted changes under `.specs/decisions/` and in `CONTEXT.md`.

   ```gherkin
   Scenario: REV-01.S1 snapshot includes records and glossary
     Given a fixture repository with a committed spec and tasks for feature demo
     And uncommitted edits to .specs/decisions/0001-demo.md, .specs/decisions/summary.md and CONTEXT.md
     When prep_review.py spec demo runs
     Then it exits 0
     And the HEAD commit contains those three paths
   ```

### P1: Tasks and Tickets at every scope ⭐ MVP

**User Story**: As a developer who reviews work through `tasks.md`, and as the product team following progress, I want every Spec to have Tasks grouped into day-sized Tickets that can be published to our tracker, so that both of us can follow and reference the work.

**Why P1**: The user reviews work through `tasks.md`, and the product team needs Tickets.

**Acceptance Criteria**:

1. **TKT-01**: IF a feature has no `tasks.md` THEN `prep_review.py spec` SHALL stop with a `STOP` message naming `tasks.md`, at every scope.

   ```gherkin
   Scenario: TKT-01.S1 small spec without tasks
     Given a fixture repository with a Small-scope spec for feature demo and no tasks.md
     When prep_review.py spec demo runs
     Then it exits 1
     And its output starts with "STOP" and names tasks.md
   ```

2. **TKT-02**: IF a Medium, Large or Complex feature has no `design.md` THEN `prep_review.py spec` SHALL stop with a `STOP` message naming `design.md`.

   ```gherkin
   Scenario: TKT-02.S1 medium spec without design
     Given a fixture repository with a Medium-scope spec and a tasks.md for feature demo and no design.md
     When prep_review.py spec demo runs
     Then it exits 1
     And its output starts with "STOP" and names design.md
   ```

   ```gherkin
   Scenario: TKT-02.S2 small spec needs no design
     Given a fixture repository with a Small-scope spec and a tasks.md for feature demo and no design.md
     When prep_review.py spec demo runs
     Then its output does not name design.md in a STOP message
   ```

3. **TKT-03**: IF a task in `tasks.md` is listed in no Ticket THEN `validate_tasks.py` SHALL exit 1 naming the task.

   ```gherkin
   Scenario: TKT-03.S1 orphan task
     Given a tasks.md with tasks T1 and T2 and one Ticket K1 listing only T1
     When validate_tasks.py runs on it
     Then it exits 1
     And its output names T2
   ```

4. **TKT-04**: IF a task is listed in more than one Ticket THEN `validate_tasks.py` SHALL exit 1 naming the task and both Tickets.

   ```gherkin
   Scenario: TKT-04.S1 task in two tickets
     Given a tasks.md whose Tickets K1 and K2 both list T2
     When validate_tasks.py runs on it
     Then it exits 1
     And its output names T2, K1 and K2
   ```

5. **TKT-05**: IF a Ticket's Blocked by names a Ticket listed after it THEN `validate_tasks.py` SHALL exit 1 naming both Tickets.

   ```gherkin
   Scenario: TKT-05.S1 forward blocking edge
     Given a tasks.md whose Ticket K1 is Blocked by K2 and K2 is listed after K1
     When validate_tasks.py runs on it
     Then it exits 1
     And its output names K1 and K2
   ```

6. **TKT-06**: WHEN the user says "publish tickets" and every Finding of the latest Spec Review has a Disposition THEN the agent SHALL create one tracker issue per Ticket in dependency order and write each issue's ID into its Ticket in `tasks.md`.

   ```gherkin
   Scenario: TKT-06.S1 publish to a local tracker
     Given setup-spec-driven configured a local-markdown tracker
     And tasks.md has Tickets K1 and K2, with K2 Blocked by K1
     And every Finding in spec-review-1.md has a Disposition
     When the user says "publish tickets"
     Then the tracker holds one issue for K1 and then one for K2
     And K1 and K2 in tasks.md each name their issue ID
   ```

7. **TKT-07**: IF the user asks to publish Tickets while a Finding of the latest Spec Review has no Disposition THEN the agent SHALL refuse and list the pending Findings.

   ```gherkin
   Scenario: TKT-07.S1 publish blocked by pending findings
     Given spec-review-1.md has SR1-F3 with Disposition "(pending)"
     When the user says "publish tickets"
     Then no tracker issue is created
     And the agent lists SR1-F3 as pending
   ```

8. **TKT-08**: WHEN the Tasks phase runs, at any scope, THEN the agent SHALL slice the Spec into Tickets of about one day each before cutting Tasks.

   ```gherkin
   Scenario: TKT-08.S1 small scope gets a ticket
     Given a Small-scope spec for "fix the export's date format"
     When the agent runs the Tasks phase
     Then tasks.md has a Tickets section with one Ticket
     And every task in tasks.md is listed in that Ticket
   ```

### P2: One implementation path

**User Story**: As a developer, I want spec-driven to be the only way an agent builds code, so that every Change is specified, reviewed and verified.

**Why P2**: The core flow works without it, but side doors erode it.

**Acceptance Criteria**:

1. **FLOW-01**: WHEN `install.sh` runs THEN it SHALL remove installed copies of `ask-matt`, `implement`, `to-spec`, `to-tickets`, `triage`, `wayfinder` and `setup-matt-pocock-skills`.

   ```gherkin
   Scenario: FLOW-01.S1 retired skills removed
     Given a temporary Claude config directory whose skills/ holds ask-matt, implement, to-spec, to-tickets, triage, wayfinder and setup-matt-pocock-skills
     When install.sh runs with that directory
     Then none of those seven skill directories exist
   ```

2. **FLOW-02**: WHEN `install.sh` runs THEN it SHALL install the `grilling` and `setup-spec-driven` skills.

   ```gherkin
   Scenario: FLOW-02.S1 new skills installed
     Given an empty temporary Claude config directory
     When install.sh runs with that directory
     Then skills/grilling/SKILL.md and skills/setup-spec-driven/SKILL.md exist in it
   ```

3. **FLOW-03**: WHEN Execute works a Task that proves a Scenario THEN the agent SHALL run that Scenario's test and see it fail before writing the code that makes it pass.

   ```gherkin
   Scenario: FLOW-03.S1 red before green
     Given an approved Task T3 that proves Scenario CSV-02.S1
     When the agent executes T3
     Then the agent reports a failing run of the CSV-02.S1 test before any production edit
     And a passing run after it
   ```

4. **FLOW-04**: WHEN `diagnosing-bugs` confirms a root cause THEN the agent SHALL hand the repro, root cause and seam to a Small Specify and SHALL NOT apply the fix.

   ```gherkin
   Scenario: FLOW-04.S1 diagnosis hands off
     Given diagnosing-bugs has a red-capable repro for "export dates are off by one day"
     When the hypothesis "UTC conversion in format_date" is confirmed
     Then the agent starts a Small Specify whose first Scenario is the repro
     And no production file has changed
   ```

5. **FLOW-05**: WHEN the Verifier passes THEN the agent SHALL tell the human that `/code-review` is available and SHALL NOT run it.

   ```gherkin
   Scenario: FLOW-05.S1 human-only change review
     Given the last Task of csv-export is committed
     When the Verifier writes validation.md with PASS
     Then the agent's message says /code-review is available
     And no change-review file is created
   ```

**Independent Test**: Run `install.sh` against temporary config directories; run Execute and diagnosing-bugs on fixture repositories.
